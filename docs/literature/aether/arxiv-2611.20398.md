# Deploying a Control-Logic LLM Assistant in Air-Gapped Power Plants: Lessons in Source Authority and Bounded Retrieval

- **Key:** arxiv-2611.20398
- **Authors / organisation:** Yiwei Fu, Nicholas Gabriel; GE Vernova Advanced Research Center, Niskayuna, NY (extended version of a paper accepted to IAAI-27)
- **Date:** 2026-11-16
- **Link:** https://arxiv.org/abs/2611.20398
- **Kind:** paper (deployment / experience report)
- **Read from:** full text (HTML: abstract, §§1–7, references, Appendices A–C, Tables 1–3)
- **Relevance to us:** 1 (background) — the empirical case is an alignment problem (read-out versus the source it is calibrated against) in an industrial deployment rather than a model-internals paper; it earns the slot on two measured results that transfer to how we build and report read-outs, not on interpretability method.

## What they wanted, and why
Engineers diagnosing a plant trip trace backward through control logic — tens of thousands of typed function blocks wired by named signals — and the tracing alone can take hours. The authors want a language-model assistant for that tracing that runs entirely inside an air-gapped operational-technology network on modest on-premises hardware, and that never reports a dependency it cannot point at in the plant's own engineering data. Two constraints do the real work: the data cannot leave the site, and a wrong causal claim in an incident review is worse than no claim. Their larger point is a division of labour for high-consequence settings — the model interprets the request and phrases the answer, deterministic software builds and traverses the evidence.

## What they studied
No trained model of their own is the object of study. The unit of analysis is a **representation**: a property graph built from the controller's native Block Pin Report (a CSV with one row per block pin), with blocks, signals, a four-level execution hierarchy (device, program, task, block) and two edge types (signal feeds block, block writes signal), pins folded into edge properties. The primary unit is one gas-turbine controller (168,220 CSV rows; 28,189 block nodes, 29,721 signal nodes, 58,644 total nodes, 116,107 edges); the plant-level graph covers seven controllers (97,005 blocks, 120,742 signals, 221,406 total nodes, 402,240 edges, 812,547 CSV rows). The models appear only as components: Qwen 3.5-397B-A17B and Gemini 3.1 Pro as document extractors, and Qwen 3.5-35B-A3B in FP8 on a single GB10 with 128 GB unified memory as the local answerer.

## How they did it
Construction parses the CSV in a single pass, keys blocks by a four-part composite identifier (so a name like RUNG_1 appearing in more than 150 program–task contexts does not collide), derives signal-flow edges from each row's usage and connection columns, deduplicating on the signal-block-pin triple, and lifts equations out of a constant pin into a block property by regex. Query handling is four stages: classify the request into one of eight fixed operations (inspect a block or signal, list a signal's producers or consumers, trace upstream, trace downstream, path between two nodes, subgraph), resolve every named entity in parallel by exact then containment match, execute a dedicated Cypher query with hard bounds (10 hops of trace depth, BFS frontier of 8, 150 nodes total, 16 on shortest-path length, with a flag recording any truncation), then have the model phrase an answer over the serialised evidence. Ambiguous short block names return the candidate scopes instead of a silent pick, and unsupported requests earn an abstention rather than the nearest operation. Two earlier prototypes are then reconstructed in detail: **Prototype 1** rendered all 6,979 pages of the exchanged control-logic PDF as images and asked a VLM for blocks, signals, connections and equations as JSON, scored against the CSV-derived graph; **Prototype 2** was a tool-calling agent over the same graph with block, signal, path and arbitrary-Cypher tools, compared against the bounded pipeline on 40 template-generated questions drawn from a 6,860-node neighbourhood around one alarm, run three times each, with the same answer model and the same evidence-grounded prompt, scored by an LLM judge (DeepEval GEval) against references synthesised from each question's expected subgraph.

## What counts as an explanation here
A **retrieved subgraph plus an ordered dependency chain plus activation conditions**: from a named protection signal, the set of upstream blocks and signals with the block equations written out and the inputs each equation needs, rendered interactively, with the prose answer clearly subordinate. The authors are explicit that this is partial in a precise way: the graph exposes the *programmed* dependencies through which a condition can propagate, and the deterministic guarantee covers the graph payload after intent and entity selection — never the wording. Which of several possible upstream conditions actually occurred is left to runtime historian data and engineering judgement, and the system is read-only and advisory by design, unable to write to the control system.

## How they judged success
Two instruments. For extraction: precision of blocks, signals and connections against the CSV-derived graph plus exact-equation accuracy, **precision only, because export records cannot be aligned to individual pages, so recall is unknown** — a limitation they state rather than paper over. For retrieval: mean LLM-judged answer correctness, p50/p95 latency, mean tokens per query, mean database round-trips, and **cross-run Jaccard overlap of the retrieved node set**, which is the measure that separates a stochastic planner from a fixed pipeline. Controls: same graph, same answer model, same prompt, three repeats, a 100-page seeded sample shared by both extractors, and a single retrospective incident replay as the field evidence. No human scoring, no measured change in operator response time or plant availability, both acknowledged.

## What they found
**Extraction from the rendered document is a precision disaster at scale.** Qwen's connection precision was 0.41 on a 100-page sample and 0.51 over all 6,979 pages, with equation accuracy **falling from 75% on the sample to 36% on the full document**; Gemini reached 0.24 connection precision and 4% equation accuracy on the shared sample. Block precision stayed high (0.95–0.97 / 0.90), which is exactly why page-local inspection looked convincing: the visible objects were right and the relations between them were not. Full-document extraction cost 3.1 h on four H200s (about $124) against **under 10 s** for ingesting the native export of the same controller; 65% of the PDF's pages were not diagrams at all and yielded spurious entities. **Planning where the operation set is enumerable costs accuracy as well as time.** Against the tool-calling agent, the bounded pipeline scored 94% vs 85% answer correctness, cut p50 latency 14.2 → 4.8 s and p95 108.6 → 12.7 s, mean tokens per query 24K → 1.2K, and database round-trips 9.1 → 2.0, while retrieving **identical node sets across repeats (Jaccard 1.0 vs 0.61)**; the agent issued between 0 and 31 graph calls and sometimes answered without retrieving anything. The deployed graph is in use for post-trip and alarm analysis at two plants, and one replayed October 2025 compressor-bleed-valve trip shows the intended split: the graph returned the valve-position-deviation input and its rung logic, and archived historian values established that the valve had not moved.

## Limits and open problems they name
One vendor's control format; one template-generated query workload centred on a single alarm; answer quality scored by an LLM judge over generated references, so the correctness numbers are a comparative development measure rather than field accuracy; extraction measured for precision only; one retrospective incident; no usage telemetry permitted off-site, so no measured operational benefit; control logic and code proprietary and unreleased. They also bound their own rule: a VLM is still the right tool when no structured source exists, and an agent when the decomposition genuinely cannot be enumerated — the argument is about known, enumerable operations only.

## What we take from it
- **A measure**: cross-run **Jaccard overlap of the retrieved set** as the stability instrument for any procedure that lets a model choose what to look at. Two pipelines can agree on average correctness and differ completely on whether they return the same evidence twice, and only this number says so — it is the natural companion to our probe-read-out reproducibility checks.
- **A warning, quantified**: page-local plausibility is not scale validity. Block precision 0.95 with connection precision 0.41 means the *objects* of an explanation were extracted correctly while the *relations* that constitute it were wrong more often than right, and downstream stages consumed them without revalidation. Any pipeline of ours that chains read-outs — attribution feeding a circuit feeding a claim — inherits exactly this error mode, and the fix is the same: score the relation, not just the entity, and revalidate rather than consume.
- **A rule for building read-outs**: find the authoritative representation before choosing the model that reads it. A native structured export of the same controller was ingested in seconds at full fidelity where a 3.1-hour VLM pass was half wrong — "is this document the source or a rendered view of the source" is the first question, not the last.
- **A framing worth borrowing for our own harness**: confine generative freedom to intent classification and phrasing, and let fixed code produce the evidence payload, with the payload immune to rewriting. Reported honestly, this buys determinism (Jaccard 1.0) at the cost of abstention on anything the eight operations cannot express.
- **What this paper is not**: it contains no model-internals interpretability and no white-box prediction, so it speaks to how we *present and validate* read-outs, never to how we derive them.
