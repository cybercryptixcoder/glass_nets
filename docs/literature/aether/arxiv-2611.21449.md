# Replicating and Extending Weight-Space Programming: Frontier LLMs Compile Programs into Weights and Read Input Layers

- **Key:** arxiv-2611.21449
- **Authors / organisation:** Roksana Goworek, Alexander Hickey, Federico Nanni, Martin O'Reilly — The Alan Turing Institute
- **Date:** 2026-11-16
- **Link:** https://arxiv.org/abs/2611.21449
- **Kind:** paper (working note / replication report)
- **Read from:** full text
- **Relevance to us:** 2 (useful)

## What they wanted, and why
A frontier lab had recently posted that a general-purpose model can emit the weights of a small neural network in a single reply, and can name what a small network was trained to do from its raw weights. The note is a three-day replication sprint whose purpose is to separate what genuinely reproduces from what the framing oversells, and to ask whether either ability is a working tool for interpretability — specifically whether weights can be *read* to explain a model's behaviour without running it. The larger goal is shared with ours: deciding whether weight-level inspection can substitute for behavioural testing, which is exactly the question our white-box model has to answer.

## What they studied
Small networks only. Written networks: MinAtar-style grid games (Breakout, Seaquest, Asterix, plus two modified Breakout variants and three games trained in-house), architecture of 600 inputs → 32 → 32 → 6 actions, 20,486 weights; and MNIST classifiers of 784 → 32 → 32 → 10. Reader-side models: GPT-6 Astra, Claude Opus 5.5, plus Claude Opus 4.5 / 4.8 / 5, GPT-5.2 / 5.6 Sol, Kimi-K3 / K3.1-Pro, DeepSeek-V4-Pro, Qwen3.8-27B. Audit targets: Olmo 3 190M pairs (one poisoned during training, one poisoned by later fine-tuning) and Qwen3.5-0.8B LoRA adapters (mundane personas versus malicious ones; mundane versus backdoored). Unit of analysis: individual weights, first-layer input-channel weight maps, and whole networks.

## How they did it
Each model was prompted once, with no tools available, for either a Python program or a network's weights for the same game — the code-versus-weights pair is the instrument that separates "cannot play" from "cannot encode". Novelty controls: two Breakout variants (left-right swapped, board inverted) that cannot be in any training corpus, and in-house-trained networks on three new games (an asteroid descent game, Whac-A-Mole, and a row-locked shooter). Reading was then tested three ways. (i) Naming: identify the game from raw weights, against a shuffled-weight control. (ii) Mechanism recovery: on the in-house games, the same prompt was asked three times per network and answers were compared with the true mechanics, not just the layout. (iii) Decompilation: two agents, working in isolated folders with the weights, architecture, rules and input/output spec but forbidden to execute the network or simulate the game, were asked to write Python that reproduces the policy; the programs were then checked against the network on every board state they could enumerate and over 1,000 games. Auditing was run with plain-text weight files and file read/write only — no Python, no forward passes — on paired models where one is compromised; a run counts as correct when the agent names the compromised member. Finally, tokeniser identity across model generations was used as an external clue about whether the ability came from a new pretrain or from further post-training.

## What counts as an explanation here
Three distinct forms, deliberately kept apart. For written networks, the explanation is the *program the weights compile* — recoverable because the weights are sparse and near-binary, so a unit's function can be read off its sign pattern and saturation; the two independent decompilations matching each other and matching the writer's own design notes is the evidence that this form is real. For trained networks, the explanation offered by weight reading is a *layout map*: per-input-channel weight norms rendered as a heat map, giving where each object class lives on the board, which says nothing about what actions do. For audits, the explanation is a *verdict plus a stated piece of evidence* (which tensors look anomalous), and it is explicitly partial — the paper's finding is that no run reached the trigger or the behaviour.

## How they judged success
Game score over 1,000 plays against the original post's PPO baselines and against each model's own Python program; MNIST test accuracy against a trained network (96.7%) and a mean-image template classifier (82.0%); naming accuracy against shuffled-weight and chance controls, sometimes reported per game; decompilation agreement over 49,189 enumerated states and 1,000-game score match; audit accuracy against 50% chance with a binomial reading, and a separate check for whether the trigger or behaviour was ever named; run-to-run repetition (mostly 1–5 runs, single runs for programs).

## What they found
Writing reproduces: Astra's Breakout networks scored 514, 550 and 307 against the original 517, and averaged 515 on both unseen variants where the standard-game network scored 0.5 and 0.0 — so it is compiling the game's rules rather than recalling a network. The generation gap is the interesting part: by July 2026 Opus 5 wrote a 580 Breakout program but networks averaging 30.9, GPT-5.6 Sol a 301 Asterix program against 14.6; Astra's September networks keep half to two-thirds of their program scores (695.7 code against 456.9 weights on Breakout). Open-weight models lag on both sides — Kimi-K3.1-Pro averaged 439 as a program and 19–68 as weights, Qwen3.8-27B under 5 points with a best of 41 in 96 runs. Written networks are sparse (4% and 6% of weights set for the two good writers; 815 of 20,486 non-zero in Astra's) with magnitudes in the hundreds, against PPO networks that set nearly all weights at a median 0.08 — a structural difference, and the two independent decompilations matched Astra's network in all 49,189 states and over 1,000 games. On digits, with no program to compile, Astra averaged 49.6% (55.7 / 47.2 / 46.0), below the 82.0% template baseline; the rotated-digit control scored the same 49.4% and failed upright digits, so it was a genuine compile for that input. Reading is mostly the first layer: naming reproduces (12 of 12 for Astra and Opus 5.5, chance under shuffling), but on the three in-house games Astra always recovered the layout (nine holes in Whac-A-Mole, the six the undertrained network actually used) and consistently missed the mechanics — which action whacks, what fires hazards — and fell back on a familiar name (Frogger, Asterix-like) when the mechanics did not fit; Qwen3.8-27B got partial layout in 3 of 10 and 2 of 10 runs. Audits: Astra found the model poisoned at pretraining in 10 of 10 runs (on evidence it flags, special-token embeddings that look initialised versus trained — plausibly payload traces, not the trigger), the later-fine-tuned one in 7 of 10 (not better than chance), the malicious persona adapter in 23 of 32, and the backdoored adapter at 13/32 and 17/32 — indistinguishable from chance — while no run in either task named the trigger or described the behaviour. Qwen3.8-27B reached 23 of 28 on the easiest poison task and was at chance on the harder ones (8/21 fine-tuned, 14/32 personas).

## Limits and open problems they name
A three-day sprint with one to five runs per cell and single runs for programs; code was written largely by the same model families being evaluated and not independently reviewed; the decompilation restrictions were instructions rather than enforced sandboxes, and one agent later confirmed they were not breached; models are proprietary and the versions tested describe November 2026; all networks are small and only one fuzzy task was used, so the boundary of these abilities is open; the original post's networks and logs are now public, so later models may have seen them; the cause of the capability (post-training, exposure to the interpretability literature) is inferred from tokeniser identity and is not proven; whether Astra's fallback naming reflects priors or genuine resemblance of the new games to familiar ones is left open.

## What we take from it
A method, a framing and two warnings. The method is the **code-versus-weights pair**: ask for the same behaviour as a program and as a representation, and the gap tells you whether a failure is about capability or about encoding — we can run the analogous pair on our own tasks (a probe versus a verbalised rule). The decompilation protocol is the strongest cheap explanation check we have seen: give two independent readers the weights only, forbid execution, then verify the recovered program on exhaustively enumerated inputs — that is a complete, checkable explanation with no behavioural oracle in the loop, and it is available to us for any mechanism claim on a small network. The framing to adopt is that **an explanation should be graded by which tier it reaches** — layout ("where things are"), mechanics ("what actions do"), and trigger ("what makes this model misbehave") — because here the first tier is nearly solved and the other two are at chance, and a result that reports only the first reads as a complete audit. The first warning is for our probes: first-layer weight norms are a heat map that a human can read with a few lines of NumPy, so a read-out that "explains" classification by locating input structure has reproduced the input, not the function — the same confound as a probe that recovers topic instead of the target property. The second is that a writer's sparse, saturated, hand-designed mechanism is **not** the distributed mechanism of a trained network, so LLM-written networks are good controlled test-beds for interpretability methods (their units are pre-labelled by design) but are not evidence that a trained network can be read.
